# Determinism and the fingerprint

The same manifest, configuration and urn-forge version always give the same bytes. This is true on any machine, in any locale and time zone, and on any date. This page tells why urn-forge needs this contract, how it keeps it, and why gate 4 compares bytes.

## Why determinism is necessary

Gate 4 compiles the manifest again and compares the result with the committed files. If the compiler gave different bytes on a different machine, gate 4 would fail on a clean repository. A developer in one time zone would commit files that CI in a different time zone refuses. The gate would then be noise, and a team would learn to ignore it.

Determinism also makes a verdict reproducible. If CI passed on a commit last month, the same commit must pass today. Specification v1.1 states it as a principle: "The same manifest, config and generator version produce byte-identical output and the same verdict, on any machine, on any date."

## The rules

The compiler and every plugin obey these rules:

- **No clock.** Specification v1.0 wrote a `compiledAt` time into the IR and the file headers. Version 1.1 removed it, because a time stamp makes each compile different.
- **No randomness, and no environment.** A plugin does not read `process.env` or a path that depends on the machine.
- **Pure plugins.** A plugin is a function of the IR and its own configuration. It returns file contents, and the engine writes them. The engine itself does not touch the file system. The CLI writes what the engine returns.
- **Sorted output.** Object keys, URN lists and declarations follow a fixed order. The fields of an entity keep the order of the manifest. Everything else is in URN order.
- **One text format.** Line endings are `\n`. Each file ends with one newline.

## The canonical IR

The IR is the input of every plugin and of the fingerprint, so it has one exact text form. Specification v1.0 used a `Map`, which does not serialize to JSON. Version 1.1 uses plain objects with the URN as the key.

The canonical JSON of urn-forge has these properties:

- It sorts object keys and keeps the order of arrays. The order of an array has a meaning, for example the order of the fields of an entity.
- It has no spaces.
- It accepts only plain JSON values. A `Map`, a `Date` or a number that is not finite stops the compile with an error. Such a value would otherwise give a different text on a different machine, without a sign.

## Sorts by code unit

Every sort that affects the output uses `compareCodeUnits`. This function compares the UTF-16 code units of two strings. It does not use `localeCompare`, because the order of `localeCompare` depends on the locale. In Turkish, for example, the upper case of `i` is `İ`, not `I`. A sort by locale could give one order on a laptop and a different order in CI.

## The fingerprint

The second line of each generated file holds a fingerprint:

```ts
// @generated by urn-forge 0.1.0 — do not edit
// fingerprint: sha256:c110f19b1800b8549c8c8fa52e6821085bc6e6a7da3e2e377936f061c24e8b70
```

The fingerprint is the SHA-256 hash of the canonical JSON of five inputs:

| Input | Why it is an input |
| --- | --- |
| The IR | It holds everything that the manifest says |
| The configuration of each plugin | A different plugin configuration can give different output |
| The urn-forge version | A new compiler can give different output |
| The name and version of each plugin | A plugin can change its output without a change to urn-forge |
| The registries: the constraint keys of each primitive, and the names of the kinds | The generated code depends on them. Refer to the next section |

The configuration input holds the configuration of each plugin, not the whole configuration file. Paths and `boundaryCoverage` do not change the generated files, so they are not inputs. The boundary rules of the primitives are not inputs for the same reason.

The IR also holds a `manifestHash`. It leaves out the kind groups that are empty. Thus a new kind in urn-forge does not change the hash of a manifest that does not use the kind.

### Why the registries became an input

At first, the fingerprint had four inputs. The project then added the `boolean` primitive, as a test of the primitive registry. The generated runtime lists every primitive in its `FieldInfo` type, so the bytes of every runtime file changed. But no manifest, configuration or version changed, so the fingerprint stayed the same.

Gate 4 still found the drift, because it compares bytes. But the header no longer described the input that made the file. A person who compared two fingerprints would see no difference between two different files.

The fix made the registries the fifth input. Now a new primitive, a new constraint or a new kind changes the fingerprint in every header. Nobody has to remember to increase a version number.

## The locale and time-zone test

A rule is only as good as its test. urn-forge tests determinism in two places:

- `tests/determinism.test.ts` compiles every fixture that passes in a child process, under the Turkish locale `tr_TR.UTF-8` and the time zone `Pacific/Chatham`. Then it compares each file with the expected bytes.
- The CI job `determinism` runs the full test suite under the same settings. Then it compiles the math example and `self/` again, and fails if `git diff` shows a change. Then it runs `verify` on both domains.

The locale and the time zone are unusual on purpose. Turkish changes the rules for case and for the order of letters. Chatham is 12 hours and 45 minutes ahead of UTC, so a date that depends on the time zone moves to a different day.

## Why drift is a byte comparison

Gate 4 compiles the manifest into a temporary directory and compares each file byte for byte with the committed copy. It also fails on a committed generated file that the compile no longer makes.

Specification v1.0 had two mechanisms for drift that did not agree: a `git diff`, and a hash of the manifest. A hash of the manifest cannot see a hand edit, or a new generator. A check of the fingerprint in the header is also not sufficient. A hand edit below the header does not change the header.

For example, a person edits one message on line 125 of the generated runtime of `self/`. Gate 4 finds the edit:

```
gate 4  drift         FAIL  2 generated file(s) compared byte for byte against self/generated
    self/generated/domain.runtime.generated.ts:125:1  error  generated-differs  differs from a fresh compile (hand-edited or stale); run `urn-forge compile`
verify failed: gate 4
```

The first two lines of the edited file, with the fingerprint, are the same as before the edit.

A byte comparison finds every difference, whatever its cause. Its cost is a full compile at each `verify`. The engine compiles in memory, and gate 4 writes only the temporary files.

## The limits

- The contract covers the output of urn-forge. The verdict of gate 1 also depends on the TypeScript version that the project installs, and gate 3 depends on the Gherkin parser.
- Specification v1.1 also defines a `referenceDate` for lifecycle checks. urn-forge does not have lifecycle data or `referenceDate` at this time. Refer to [Scope](../reference/scope).
