# How urn-forge is built

This page is for people who want to change urn-forge. It tells how a manifest becomes generated files and a verdict. It also tells how the registries hold the knowledge about each primitive and kind, and how `tsc` keeps the registries complete. The code is in `packages/urn-forge/src`.

## The pipeline

`compile` and `verify` share one pipeline. Each stage reads only the result of the stage before it:

```
domain.manifest.yaml
   │
   ▼  pass 1: meta-schema          src/meta-schema.ts, the schema of each kind
   │
   ▼  passes 2–4, 6, 7: IR builder  src/ir/build.ts, the build of each kind,
   │                                src/rules/ for invariant rules
   │
   ▼  pass 5: structure            src/ir/structure.ts, keys and cycles
   │
   ▼  pass 8: lifecycle            src/ir/lifecycle.ts, with the reference date
   │
UniversalIR (canonical, sorted by URN)
   │
   ▼  live IR                      liveIr in src/ir/lifecycle.ts: no sunset atoms
   │
   ▼  support check                src/engine.ts, the `supports` of each plugin
   │
   ▼  plugins: valibot, fcis,      src/plugins/
   │           postgres
   │
   ▼  header, line endings, sort   src/engine.ts
   │
generated files ──▶ compile writes them      (src/cli.ts, src/write.ts)
                └─▶ verify gives them, with the IR and the feature index,
                    to gates 1, 3 and 4       (src/verify/)
```

The stages have these jobs:

1. **The meta-schema** (pass 1) validates the structure of the manifest with Valibot. It builds its schema from the descriptor of each kind and each primitive.
2. **The IR builder** expands the short keys (pass 2), checks that URNs and brand identifiers are unique (pass 3) and resolves each reference (pass 4). Then each kind builds its IR node. The build runs the checks that belong to one kind. Pass 6 examines the rule of an invariant, and the message placeholders and the `recordAs` event of an error. Pass 7 examines the constraint conflicts and coherence of a field. An entity, an event or an error also examines the name and the `many` of each field reference, and an entity examines its `key`.
3. **The structure check** (pass 5) runs after each node is built, because each of its checks reads a different entity. A link and a unique list of an embedded entity need a target with a `key` (`missing-key`). No entity can embed itself (`embedding-cycle`). The pass runs only if the builder found no error.
4. **The lifecycle check** (pass 8) runs last. Pass 4 records each reference that it resolves, and pass 8 compares the `status` of the two ends of each reference. It also compares each `sunsetDate` with the reference date, if the CLI or the configuration gives one. Its warnings go on with the IR. Its errors stop the build.
5. **The live IR** is the IR with no sunset atoms. The plugins and the gates get it, so a sunset atom makes no code and needs no handler. The full IR stays in `CompileResult.ir`. The live IR depends on `status` only, never on a date, so the generated bytes do not depend on the day.
6. **The support check** compares the IR with what each plugin says that it supports. It runs before any plugin writes output.
7. **The plugins** each turn the IR into file contents. They do not read the YAML, and they do not read the output of a different plugin.
8. **The engine** adds the `@generated` header with the fingerprint, sets the line endings and sorts the files by path. The header uses the line comment of the file: `--` for a `.sql` file, and `//` for each other file. `commentMarker` in `src/engine.ts` picks it from the file extension.

The engine has no access to the file system, the clock or the environment. The CLI writes what the engine returns. `src/write.ts` knows the two forms of the header, so `compile` and gate 4 find an orphan SQL file as well as an orphan TypeScript file. This keeps the engine deterministic. Refer to [Determinism and the fingerprint](./determinism).

`verify` compiles in memory, then builds one context for all gates: the live IR, the fresh files, the paths and the feature index. Each gate is an entry in the `GATES` registry, with a number, a name and a `run` function. A gate passes when none of its problems is an error. Thus a gate can give warnings and notes and still pass. Boundary coverage needs this for its warn-then-ratchet mode.

## The diff

`urn-forge diff` is gate 5, but it is not in the `GATES` registry. A gate gets one IR, and `diff` needs two. `src/diff/index.ts` compiles the two manifests with `buildIrFromSource`, with no reference date and no plugins. `src/diff/classify.ts` then compares the two IRs:

1. `usesOf` walks the operations of the live IR of the old manifest, as gate 3 does. Each atom gets its uses. In comes from the input. Out comes from the output, the declared errors, the events and the `recordAs` events. Stored comes from the `tables` of the `postgres` plugin.
2. Each change gets a relation to the old set of values: equal, narrower, wider or neither. `src/diff/relation.ts` holds one comparison for each primitive, as `{ readonly [P in Primitive]: … }`. A new primitive thus makes `tsc` fail there until it has a comparison.
3. The relation and the uses give the class. A change with no relation, for example a removed atom or a lifecycle step, gets its class directly.

The CLI reads only the `tables` of the `postgres` plugin from the configuration. It turns the classes into lines, and each breaking change into the diagnostic `breaking-change`.

## The registries

The [foundations plan](../project/foundations-plan) found that the knowledge about each primitive was in six places, and nothing kept them in step. The meta-schema, the IR types, the Valibot plugin, the FCIS plugin and the step library each had a list of primitives. The IR builder also had a branch for each kind.

The plan put each kind of knowledge in a registry:

| Registry | Where | One entry holds | Consumers |
| --- | --- | --- | --- |
| Primitives | `src/primitives/` | The constraints, with the schema and the aspect of each constraint value, the groups of constraints that exclude each other, coherence (pass 7), the parse of one value of a table cell, the boundary cases | The meta-schema, the IR, the plugins, the step library, gate 3 |
| Kinds | `src/kinds/` | The schema of an entry, the reference slots, the build of the IR node | The meta-schema, the IR builder |
| Plugins | `src/plugins/index.ts` | A plugin, by name | The configuration file, the engine |
| Gates | `src/verify/index.ts` | A gate, by number | `verify` |

A reference slot is a path in an entry and the kinds that it can name, such as `{ path: ['fields', '*', 'ref'], targets: ['field', 'entity'] }`. Pass 4 is one loop over the slots of every kind. A new kind brings its slots, and it gets reference checks, with positions, with no new pass code. The `invariant` kind got the check of its `on` in this way.

### The build stages

Most kinds build their node from their own entry and the atoms that their references name. An invariant needs more: to type its rule, it reads the built nodes of its entity and of the fields of that entity. An error also needs more: to examine its `recordAs`, it reads the built node of the event. A descriptor can thus declare `after`, the kinds whose nodes it reads. The builder builds such a kind in a second stage, after all other atoms. The build function reads a node with `node(kind, urn)` of its build context.

There are only two stages, not an order computed from the `after` lists. Two kinds use `after` at this time, and neither reads the other, so a general sort would be code with no use. The stage also sets the sequence of the diagnostics: the problems of the invariants and the errors come after the problems of the other atoms.

### The rule language

The rule language is in `src/rules/`, apart from the kinds and the plugins. `src/rules/index.ts` has the parser, the printer of the canonical text and the type checker of pass 6. The type checker does not read the IR. It gets a map from each property name to its primitive, `required` and `many`. `src/rules/emit.ts` translates a rule to TypeScript for the Valibot plugin. The parser and the type checker do not depend on a plugin.

Gate 3 does not run the rules. Only the generated code runs them. If the type checker and the translation disagree, a rule can compile and mean something else at run time. The rules test fixture thus has one invariant for each operator on each primitive, and a test runs each generated rule at its edges.

### How `tsc` keeps the registries complete

The foundations plan used the idea of urn-forge on urn-forge itself. Gate 1 uses `tsc` to find a handler that is not there. In the same way, each consumer that must handle every primitive or every kind declares a table that `tsc` checks:

- The Valibot plugin declares its translations as `{ readonly [P in Primitive]: ValibotTranslation<P> }`. Each translation has one entry for each constraint of its primitive. A new primitive or constraint makes `tsc` fail at this table until it has an entry.
- The Postgres plugin declares its domains in the same way, as `{ readonly [P in Primitive]: DomainTranslation<P> }`. A new primitive makes `tsc` fail until it has an SQL type and its conditions.
- The kind registry uses `satisfies { readonly [K in KindName]: KindDescriptor<K, any, unknown> }`. A new name in `KindName` makes `tsc` fail until the registry has a descriptor.
- A type-level check compares the groups of the kind registry with the records of `UniversalIR`. If the two disagree, `tsc` fails.
- Each member of a descriptor is necessary. When `boundaries` became a member of the primitive descriptor, `tsc` named all four primitives of that time until each had its rules.

Some rules are not types, so tests keep them. Each constraint declares its aspect, for example `range` or `shape`. A test makes sure that one constraint name has the same aspect on each primitive, and that the constraints of one exclusive group share one aspect. A second test compares the constraint table of [Primitives and constraints](../reference/primitives) with the registry, row for row. For the model behind the aspects, refer to [The MECE model of primitives](./primitives-model).

CI runs `npm run typecheck`, so these checks fail the build, and not only the editor.

## What a plugin supports

Specification v1.1 says that each plugin "must handle every IR construct or fail compilation naming the construct it cannot handle". A plugin that skips a construct without a sign is worse than a plugin that fails. The generated code would look complete, but it would not be.

Each plugin thus declares `supports`: the kinds that it handles and, for each primitive, the constraints that it translates. Before any plugin writes output, the engine compares the IR with these declarations. Each construct that a plugin does not support becomes an `unsupported-construct` diagnostic, with its URN and its position in the manifest.

The Valibot plugin derives its `supports` from its translation table. Thus the declaration and the code that writes the output cannot disagree. The Postgres plugin declares the six kinds and no constraint list, because its domain table has an entry for each primitive. Operations, events and errors are not stored, so the plugin writes nothing for them.

A plugin can also report its own diagnostics from `emit`. The Postgres plugin examines its `tables` option there, because only the IR can tell if a short key names an entity with a `key`. It also reports `unenforced-in-sql` for each rule that has no exact SQL form. A plugin that cannot write a rule says so. It does not write an approximate rule.

The configuration type of a plugin is the input type of its `configSchema`. `CodegenPlugin<C, I>` has `C`, the configuration that `emit` gets. It also has `I`, the configuration that a person writes. For `postgres`, `I` has the optional `tables` and `unenforced`, and `C` has both with their defaults. `defineConfig` uses `I`, so a configuration can leave out an option that has a default.

A plugin also declares `requires`: the plugins whose output its own output imports. The FCIS runtime imports the Valibot schemas. If a configuration enables `fcis` without `valibot`, the compile stops with `missing-plugin`.

The support check also made it possible to add the `error` kind in small steps. When the compiler first accepted errors, no plugin supported them. A manifest with an error stopped with `unsupported-construct` from both plugins. After the next step, it stopped with a diagnostic from the FCIS plugin only. After the step after that, it compiled.

## The feature index

Gate 3 needs the features in a form that it can compare with the IR. `src/verify/feature-index.ts` parses every `.feature` file once, with `@cucumber/gherkin`. The index holds these parts of each feature:

- The scenarios, with their tags in scope.
- The steps of the background and of each scenario.
- The tables, with the position of each cell.
- The `Examples` values.
- The comments.


Gate 3 reads the index for tags, headers, declared errors, broken invariants and waivers. `inputValues` reads the same index to collect the values that each operation receives, for boundary coverage. It converts each cell with the primitive of its field, as the steps do.

The steps and gate 3 use one cell reader, `src/gherkin/cells.ts`, for list and object cells. The reader parses the brackets, the braces and the quoted values. Then it reads each value with the primitive of its field. Thus a malformed cell fails in Cucumber and in gate 3 (`invalid-cell`) with the same message.

The texts of the generic steps are in `src/gherkin/phrases.ts`. The step library registers these texts, and gate 3 reads them to find the input table of a scenario. Thus the step library and gate 3 cannot disagree about which table is the input.

## Why a new primitive or kind is one place

The registries make breadth additive. The first additions after the foundations work show this:

- **`boolean` with `mustBe`.** It took one module in `src/primitives/`, one line in the registry and one entry in the Valibot translations. `tsc` named that table and nothing else. The meta-schema, `FieldInfo`, the cell parse and the support check took it with no change.
- **`oneOf` on `string`.** It was the first constraint whose value is not a number. It took the constraint in the `string` descriptor and one Valibot entry. `tsc` typed the value as `string[]` in that entry. Later, the `enum` primitive replaced it, also as one module and one Valibot entry.
- **`decimal`, `date` and `timestamp`.** Each took one module, one registry line and one Valibot translation. Their schemas call helper functions, so the Valibot translation also names the helpers that each primitive needs. The plugin writes a helper only if a field uses it.
- **The `event` kind.** In an early trial, `tsc` asked for a descriptor, a registry entry and an IR group. The kind then got reference checks with no new pass code. The real kind later used the same field references as an entity, and the payload form of an error. The Valibot plugin thus writes an event with the function that writes an error.

A list is not a primitive, so it is not one place. `many` on a field reference changed the IR, both plugins, the step library and gate 3. The list belongs to the reference, not to the value, so the primitive registry does not hold it.

## Three forms of a reference

The [structure plan](../project/structure-plan) added embedded entities and links on the same axis as lists. A field reference in the IR is thus one of three forms, `IRPropertyRef`:

| Form | Manifest | Target key |
| --- | --- | --- |
| `IRFieldRef` | `ref: <field>` | `field` |
| `IREmbedRef` | `ref: <entity>` | `entity` |
| `IRLinkRef` | `link: <entity>` | `link` |

Each form has `name`, `required` and `many`. The target key tells the forms apart, so a consumer examines `'entity' in ref` or `'link' in ref`.

`IRFieldRef` kept the shape that it had before, `{ field, name, required, many? }`. Code that reads only field values did not change, and the IR of a manifest with no structure did not change either. A tagged union with a new `kind` property would have changed each reference in each IR and each fingerprint, for no new information. The target key is already a tag.

Most consumers want the field whose values a property holds. For a link, that is the key field of the linked entity. The function `valueField(ir, ref)` gives it, so each plugin and gate does not derive it again. An embedded entity has no value field. Each consumer that reads it walks into the entity: the Valibot plugin uses the entity schema, the FCIS plugin writes an `EmbeddedInfo`, and gate 3 counts the nested values.

The change touched every layer: the kinds, the rules, both plugins, the steps and gate 3. No layer could take the new forms alone, so the build was one commit. The three forms in one place in the IR kept the change small in each layer.

The registries do not hold speculative properties. A property goes into a descriptor when a part of urn-forge that is not a plugin needs it. Boundary cases came with gate 3, and not before. Plugin details stay in the plugins.

## The limits

- urn-forge has no API for plugins from other packages. The plugins are part of the repository, and their names are typed by the registry.
- Pass 5 finds only cycles of embedded entities. A cycle of links is correct, and no other kind can make a cycle.
- A new kind is still more work than a new primitive. Each plugin must decide what to write for it. The `error` kind changed both plugins, the step library and gate 3. The `invariant` kind changed the same parts, and it added the build stages and `src/rules/`. The `event` kind changed the same parts and `urn-forge diff`, and it added a type argument to `Result`.
