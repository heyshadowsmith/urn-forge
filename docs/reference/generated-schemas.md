# The generated schemas

The Valibot plugin (`valibot`, version 0.1.0) writes the file `domain.schemas.generated.ts` in the `--out` directory. The file has one Valibot schema and two types for each field, entity and error of the manifest. Operations have no declarations in this file. This page gives the form of each part of the file. For the reasons for the brands, refer to [The functional core and brands](../explanation/functional-core).

## The file

| Item | Value |
| --- | --- |
| File name | `domain.schemas.generated.ts` |
| Plugin | `valibot`, version `0.1.0`. The plugin accepts only the configuration `{}` |
| Import | `import * as v from 'valibot';` |
| Imported by | The generated runtime file, as `./domain.schemas.generated.js`. Refer to [The generated runtime](./generated-runtime) |
| Text format | UTF-8 with no byte order mark, `\n` line endings, and one `\n` at the end of the file |

Do not edit this file. Gate 4 compares it, byte for byte, with a new compile. Refer to [Verification gates](./verification-gates).

## The header

Each generated file starts with the same two lines. The `compile` engine adds them, not the plugin:

```ts
// @generated by urn-forge 0.1.0 — do not edit
// fingerprint: sha256:6c451e521ca60fdcbfbb38f9a7cc41e23de3a9ee6e62323bc7aa67033f70bf4e
```

| Line | Form | Description |
| --- | --- | --- |
| 1 | `// @generated by urn-forge <version> — do not edit` | The version of urn-forge that made the file |
| 2 | `// fingerprint: sha256:<64 hexadecimal digits>` | The SHA-256 hash of the canonical JSON of the compile inputs. The two generated files have the same fingerprint, and `compile` shows it on its last line |

An empty line follows the header. The fingerprint is a hash of these inputs:

- The canonical IR of the manifest.
- The name and configuration of each plugin, in the sequence of the plugin list.
- The urn-forge version.
- The name and version of each plugin.
- The primitives with their constraint names, and the kinds, that urn-forge knows.

For the reasons for the fingerprint, refer to [Determinism and the fingerprint](../explanation/determinism).

## The sequence of the declarations

| Position | Content | Present |
| --- | --- | --- |
| 1 | The header and an empty line | Always |
| 2 | `import * as v from 'valibot';` | Always |
| 3 | `// Fields`, then one declaration for each field | Always. The comment is there also if the manifest has no fields |
| 4 | `// Entities`, then one declaration for each entity | Always. The comment is there also if the manifest has no entities |
| 5 | `// Errors`, then one declaration for each error | Only if the manifest has one or more errors |

In each group, the declarations are in URN sequence. The sort compares UTF-16 code units, not the rules of a locale. An empty line comes between two declarations. The properties of an entity or an error are in the sequence of its `fields` list in the manifest.

## Field schemas

Each field becomes one `v.pipe`:

```ts
/** <field URN> — <description> */
export const <Brand>Schema = v.pipe(
  <base actions>,
  <one action for each constraint>,
  v.brand("<field URN>"),
);
```

- The comment has ` — <description>` only if the field has a `description`.
- The base actions come first. Then each constraint becomes one action, in the sequence of the table of constraints, not in the sequence of the manifest.
- `v.brand("<field URN>")` is always the last action. The URN is a string literal in double quotes.

### Base actions

| Primitive | Base actions | Value type |
| --- | --- | --- |
| `boolean` | `v.boolean()` | `boolean` |
| `float` | `v.number()`, `v.finite()` | `number` |
| `integer` | `v.number()`, `v.safeInteger()` | `number` |
| `string` | `v.string()` | `string` |

### Constraint actions

| Primitive | Constraint | Action | Notes |
| --- | --- | --- | --- |
| `float`, `integer` | `min` | `v.minValue(<n>)` | The value is a number literal. `-0` stays `-0` |
| `float`, `integer` | `max` | `v.maxValue(<n>)` | |
| `float`, `integer` | `notEqual` | `v.notValue(<n>)` | |
| `string` | `minLength` | `v.minLength(<n>)` | The length is in UTF-16 code units |
| `string` | `maxLength` | `v.maxLength(<n>)` | |
| `string` | `regex` | `v.regex(/^(?:<pattern>)$/u)` | The pattern must match the whole value. The `u` flag is set. A `/` in the pattern becomes `\/` |
| `string` | `oneOf` | `v.picklist([<values>])` | Each value is a string literal in double quotes, in the sequence of the manifest. The output type becomes the union of the values |
| `boolean` | `mustBe` | `v.value(<true or false>)` | The type stays `boolean` |

Examples from the shop test fixture:

```ts
/** urn:demo:shop:order:field:quantity */
export const OrderQuantitySchema = v.pipe(
  v.number(),
  v.safeInteger(),
  v.minValue(1),
  v.maxValue(99),
  v.notValue(13),
  v.brand("urn:demo:shop:order:field:quantity"),
);

/** urn:demo:shop:order:field:tracking_url */
export const OrderTrackingUrlSchema = v.pipe(
  v.string(),
  v.regex(/^(?:https:\/\/track\.example\/[0-9]+)$/u),
  v.brand("urn:demo:shop:order:field:tracking_url"),
);
```

For the constraints themselves, refer to [Primitives and constraints](./primitives).

## Entity schemas

Each entity becomes one `v.object`:

```ts
/** <entity URN> — <description> */
export const <Brand>Schema = v.object({
  <property>: <Field brand>Schema,
  <property>: v.optional(<Field brand>Schema),
});
```

| Item | Rule |
| --- | --- |
| Property name | The identifier of the field, which is the last segment of its URN. For example, `urn:demo:shop:order:field:unit_cost` becomes `unit_cost` |
| Property value | The schema of the field |
| `required: false` | The plugin puts the field schema in `v.optional(…)`. The key can then be absent, or its value can be `undefined` |
| Sequence | The sequence of the `fields` list of the entity in the manifest |
| Unknown keys | `v.object` accepts a key that is not a property, and removes it from the parsed output |

```ts
/** urn:demo:shop:order:entity:line_total — The cost of one line */
export const OrderLineTotalSchema = v.object({
  total: OrderTotalSchema,
});
```

## Error schemas

Each error becomes one `v.object`. Its first property is `kind`. Then the fields of the error follow, with the same rules as for an entity:

```ts
/** <error URN> — <description> */
export const <Brand>Schema = v.object({
  kind: v.literal("<error URN>"),
  <property>: <Field brand>Schema,
});
```

- The type of `kind` is the URN of the error as a string literal, not `string`.
- An error with no fields has only the `kind` property.
- No field of an error can have the identifier `kind`. Pass 3 gives `reserved-property`. Refer to [Diagnostics](./diagnostics).
- The `category`, `retryable` and `message` of the error are not in this file. They are in `DispatchMap` in the runtime file.

```ts
/** urn:demo:shop:order:error:price_unavailable — No price is known for the item */
export const OrderPriceUnavailableSchema = v.object({
  kind: v.literal("urn:demo:shop:order:error:price_unavailable"),
  sku: OrderSkuSchema,
});
```

## The three exports of each atom

Each field, entity and error has three exports. Each name starts with the brand identifier of the atom: the PascalCase form of its context and its identifier. For the rules of the names, refer to [URNs and names](./naming).

```ts
export const <Brand>Schema = …;
export type <Brand> = v.InferOutput<typeof <Brand>Schema>;
export type <Brand>Input = v.InferInput<typeof <Brand>Schema>;
```

| Export | Kind | Description | Example for `order.field.delivery` |
| --- | --- | --- | --- |
| `<Brand>Schema` | Constant | The Valibot schema | `OrderDeliverySchema` |
| `<Brand>` | Type | The parsed type. A field type has the brand. An entity or error type has a branded type for each property | `OrderDelivery`: one of the three `oneOf` values, with the brand `v.Brand<"urn:demo:shop:order:field:delivery">` |
| `<Brand>Input` | Type | The type that the schema accepts, with no brand | `OrderDeliveryInput`, which is `string` |

Only a parse with the schema can make a value of a branded type. If two atoms make the same export name, compile fails with `export-collision`.

## Operations

An operation has no declaration in this file. Its `input` and `output` are entities, and its errors are errors, so their schemas are already in the file. The runtime file uses these schemas. Refer to [The generated runtime](./generated-runtime).
