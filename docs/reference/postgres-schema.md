# The Postgres schema

The Postgres plugin (`postgres`, version 0.1.0) writes the file `schema.generated.sql` in the `--out` directory. The file has `CREATE` statements for Postgres. It makes a schema for each context, a domain for each stored field, and tables for the configured entities. This page gives the configuration, the names, the types and each statement of the file. For the reasons for this design, refer to [The MECE model of primitives](../explanation/primitives-model) and [Departures from the specification](../explanation/departures-from-the-spec).

The plugin only writes text. It does not connect to a database, run SQL, make migrations or write code that reads and writes rows. Give the file to your migration tool.

## The file

| Item | Value |
| --- | --- |
| File name | `schema.generated.sql` |
| Plugin | `postgres`, version `0.1.0`. The plugin is not in the default plugin list. Add it to `plugins` in the configuration file |
| Necessary plugin | None. The SQL imports no other generated file |
| Postgres version | 14 or later. Refer to [Postgres version](#postgres-version) |
| Text format | UTF-8 with no byte order mark, `\n` line endings, and one `\n` at the end of the file |
| Header | The same two lines as the TypeScript files, with `--` in place of `//`. The fingerprint is the same in each file of one compile |

Do not edit this file. Gate 4 compares it, byte for byte, with a new compile. Refer to [Verification gates](./verification-gates).

The first lines of the insurance file:

```sql
-- @generated by urn-forge 0.1.0 — do not edit
-- fingerprint: sha256:f72f538c562a7bf23f518078548823cbd2d25d9125377d8c83bf9a42eebe1128

-- For Postgres 14 or later. urn-forge writes CREATE statements only: give this file to your migration tool.
```

## The configuration

The configuration of the insurance domain:

<<< @/../packages/urn-forge/insurance/urn-forge.config.ts

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `tables` | A list of short keys | `[]` | The entities that become root tables. Each item is a short key of an entity with a `key`. The entities that a table embeds become child tables. They do not go in this list |
| `unenforced` | `'warn'` or `'error'` | `'warn'` | The severity of `unenforced-in-sql`. With `'error'`, `compile` writes no files if a rule has no exact SQL form |

The configuration object cannot have other options. With `tables: []`, the file has the header and the version line only.

### Configuration errors

These messages come from a real run. The manifest has a field `shop.field.site`, an entity `shop.entity.plain` with no `key`, and an entity `shop.entity.item` with a `key`:

| Problem | Code | File of the diagnostic | Message |
| --- | --- | --- | --- |
| An item that is not a short key | `plugin-config` | The configuration file | `plugin postgres config: tables.0: must be a short key such as policy.entity.policy` |
| An unknown option | `plugin-config` | The configuration file | `plugin postgres config: unknown option "table"` |
| An incorrect value of `unenforced` | `plugin-config` | The configuration file | `plugin postgres config: unenforced: Invalid type: Expected ("warn" \| "error") but received "strict"` |
| An item that names an atom of a different kind | `wrong-ref-kind` | The manifest, with no position | `postgres config: tables[0] "shop.field.site" must name an entity, but it names a field` |
| An item that names no atom | `unresolved-ref` | The manifest, with no position | `postgres config: tables[1] "shop.entity.nope" does not resolve (no atom urn:demo:store:shop:entity:nope in this manifest)` |
| An entity with no `key` | `missing-key` | The manifest, at the entity | `urn:demo:store:shop:entity:plain: is a table in the postgres config, so it needs a key: one of its own required, single-valued fields` |
| An item two times | `plugin-config` | The configuration file | `postgres config: tables[4] "shop.entity.item" is listed more than once` |

The plugin reports each of the last four problems for each item. If one of them occurs, the plugin writes no SQL.

## The sequence of the statements

| Position | Content | Present |
| --- | --- | --- |
| 1 | The header and an empty line | Always |
| 2 | The version line: `-- For Postgres 14 or later. …` | Always |
| 3 | `CREATE SCHEMA IF NOT EXISTS "<context>";` for each context of a stored field or entity, in alphabetical sequence | If `tables` is not empty |
| 4 | A domain for each stored field, in URN sequence, with its comment | If `tables` is not empty |
| 5 | Each root table, in the sequence of `tables`, with its comments. After each table, its child tables, in the sequence of the properties, at any depth | If `tables` is not empty |
| 6 | `ALTER TABLE … ADD CONSTRAINT … FOREIGN KEY …` for each link to a root table | If a stored entity has a link to a root table |
| 7 | The functions and the constraint triggers of each count | If a stored entity has a count |

The plugin reads the live IR, so a sunset atom gets no domain, no table and no column. The stored entities are the entities in `tables` and each entity that they embed, at any depth. The stored fields are the fields of the stored entities, and the key fields of their links. A field that only other entities, events or errors use gets no domain.

The plugin accepts each kind, but it writes nothing for an operation, an event or an error. These atoms are not stored. Thus the insurance file has no statement for its three events. urn-forge does not have an event store or an outbox table at this time. Refer to [Scope](./scope).

An empty line comes before each domain and each table.

## Names

Each name is in double quotes in the SQL, so a reserved word such as `limit` is a correct column name.

| Part | Name | Example from insurance |
| --- | --- | --- |
| Schema | The context of the atom | `"policy"` |
| Domain of a field | `"<context>"."<identifier>_value"`, from the URN of the field | `"policy"."premium_value"` |
| Check constraint of a domain | `"<identifier>"` of the field | `"premium"` |
| Root table | `"<context>"."<identifier>"`, from the URN of the entity | `"policy"."policy"` |
| Column | The property name | `"holder"` |
| Primary key | `"<table>_pkey"` | `"policy_pkey"` |
| Child table | `"<parent table>__<property>"`, in the schema of the parent table | `"policy"."policy__coverages"` |
| Foreign key to the parent | `"<child table>_parent_fkey"` | `"policy__coverages_parent_fkey"` |
| Foreign key of a link | `"<table>_<column>_fkey"` | `"policy_holder_fkey"` |
| Unique constraint of a list | `"<child table>_<column>_key"` | `"policy__coverages_peril_key"` |
| Check constraint of an invariant | `"<identifier>"` of the invariant | `"term_is_positive"` |
| Count functions | `"<schema>"."<child table>_count"`, `"<child table>_count_parent"` and `"<child table>_count_item"` | `"policy"."policy__coverages_count"` |
| Count triggers | `"<property>_count"`, one on the parent table and one on the child table | `"coverages_count"` |

A child table of a child table adds one more `__<property>`. For example, a list `tags` in each item of a list `lines` of `order` is the table `"order"."order__lines__tags"`.

### `invalid-sql-name`

Postgres keeps 63 bytes of a name, and cuts the rest. The plugin refuses a name that Postgres would cut, and a name that two parts would share. It reports `invalid-sql-name` and writes no SQL.

| Check | Names | Example message |
| --- | --- | --- |
| More than 63 bytes | Domains, tables, child tables, primary keys, foreign keys, unique constraints, the key columns of a child table, the count functions and the count triggers | `urn:demo:store:shop:field:a_field_name_that_is_much_too_long_for_a_postgres_identifier: the domain name "a_field_name_that_is_much_too_long_for_a_postgres_identifier_value" is 66 bytes; Postgres keeps at most 63` |
| One name for two parts | Tables, child tables, primary keys and unique constraints in one schema. Check constraints of invariants on one table. A property of a child table with the name of a column that the plugin adds: a key column of the parent, or `position` | `urn:demo:shop:order:entity:order__lines: the table name "order.order__lines" is also a name that urn:demo:shop:order:entity:order uses` |

In the second example, the entity `order.entity.order__lines` has the name of the child table of the property `lines` of `order.entity.order`. For a property with the name `position` in an entity in a list, the message is `urn:demo:shop:a:entity:item: the column name "e__items.position" is also a name that urn:demo:shop:a:entity:e uses`.

## Types

Each field becomes a domain: the SQL type of its primitive, and one check constraint with all its constraints. Each column and each list item of the field uses the domain.

| Primitive | SQL type | Conditions that are always in the check |
| --- | --- | --- |
| `boolean` | `BOOLEAN` | None |
| `enum` | `TEXT` | `VALUE IN ('<value>', …)` |
| `string` | `TEXT` | None |
| `integer` | `INTEGER` if the field has `min` and `max`, and both fit in 32 bits. Otherwise `BIGINT` | With `BIGINT`: `VALUE BETWEEN -9007199254740991 AND 9007199254740991`, the safe integers of JavaScript |
| `float` | `DOUBLE PRECISION` | `VALUE NOT IN ('NaN', 'Infinity', '-Infinity')` |
| `decimal` | `NUMERIC`, with no precision and no scale | `VALUE NOT IN ('NaN', 'Infinity', '-Infinity')` |
| `date` | `DATE` | None |
| `timestamp` | `TIMESTAMPTZ` | None |

A `string` with `format: uuid` is also `TEXT`. A `decimal` keeps the digits that it gets: `120.00` stays `120.00`.

### Constraints as conditions

The check has the conditions of the primitive, then the conditions of the constraints, joined with `AND`. A field with no condition has a domain with no check.

| Constraint | Primitive | Condition |
| --- | --- | --- |
| `mustBe` | `boolean` | `VALUE = TRUE` or `VALUE = FALSE` |
| `values` | `enum` | `VALUE IN ('<value>', …)` |
| `minLength` | `string` | `char_length(VALUE) >= <n>` |
| `maxLength` | `string` | `char_length(VALUE) <= <n>` |
| `regex` | `string` | `VALUE ~ '^(?:<pattern>)$'`, with the pattern in the [subset](#regular-expressions) |
| `format: uuid` | `string` | `VALUE ~* '^[0-9a-f]{8}(?:-[0-9a-f]{4}){3}-[0-9a-f]{12}$'`: the pattern of `v.uuid()` |
| `format: email` | `string` | `VALUE ~ '<pattern>'`: the pattern of `v.email()`, in the subset |
| `format: uri` | `string` | None. `unenforced-in-sql` |
| `min` | `integer`, `float`, `decimal` | `VALUE >= <n>` |
| `max` | `integer`, `float`, `decimal` | `VALUE <= <n>` |
| `exclusiveMin` | `float`, `decimal` | `VALUE > <n>` |
| `exclusiveMax` | `float`, `decimal` | `VALUE < <n>` |
| `min`, `max` | `date` | `VALUE >= DATE '<day>'`, `VALUE <= DATE '<day>'` |
| `min`, `max`, `exclusiveMin`, `exclusiveMax` | `timestamp` | `VALUE >= TIMESTAMPTZ '<t>'` and the other operators |
| `multipleOf` | `integer` | `VALUE % <n> = 0` |
| `scale` | `decimal` | `scale(VALUE) <= <s>` |
| `notIn` | `integer`, `float`, `decimal` | `VALUE NOT IN (<n>, …)` |

A length counts Unicode code points in Postgres `char_length`. The Valibot schema counts code points too. Thus one emoji has the length 1 in the two checks. Refer to [Primitives and constraints](./primitives).

Two domains of the insurance file:

```sql
CREATE DOMAIN "policy"."premium_value" AS NUMERIC
  CONSTRAINT "premium" CHECK (VALUE NOT IN ('NaN', 'Infinity', '-Infinity') AND VALUE > 0 AND scale(VALUE) <= 2);
COMMENT ON DOMAIN "policy"."premium_value" IS 'urn:acme:insurance:policy:field:premium — The price of the policy for its whole term';

CREATE DOMAIN "policy"."effective_date_value" AS DATE;
COMMENT ON DOMAIN "policy"."effective_date_value" IS 'urn:acme:insurance:policy:field:effective_date — The first day that the policy covers';
```

The `postgres` test fixture has one field for each primitive and each constraint. Its generated file is `tests/fixtures/postgres/expected/schema.generated.sql`.

## Regular expressions

JavaScript and Postgres read some parts of a regular expression differently. For example, `\w` in Postgres also matches `é`, and `.` also matches a line break. The plugin thus translates a pattern only if each part of it is in a subset that SQL can express exactly. Otherwise, the field gets no shape condition, and the plugin reports `unenforced-in-sql` with the reason.

### The subset

| Part of the pattern | SQL |
| --- | --- |
| A literal character | The same character. A character that is special in Postgres gets a `\` |
| `.` | `[^\n\r\u2028\u2029]`: any character except a line terminator, as in JavaScript |
| `\d`, `\w`, `\s` | `[0-9]`, `[A-Za-z0-9_]` and the whitespace characters of JavaScript, as a class |
| `\D`, `\W`, `\S`, outside a bracket | The negated class: `[^0-9]`, `[^A-Za-z0-9_]` and the negated whitespace class |
| A bracket class, for example `[a-z]` or `[^x]` | The same class. `\d`, `\w` and `\s` in it become their ASCII ranges |
| `\n`, `\r`, `\t`, `\f`, `\v`, `\uXXXX`, `\u{…}`, `\xXX` | A Postgres escape for the same character. A character outside the Basic Multilingual Plane becomes `\U` with eight digits |
| `\` before a syntax character, for example `\.` | An escape of the same character, or the character alone if Postgres does not need the escape, for example `/` |
| `*`, `+`, `?`, `{n}`, `{n,}`, `{n,m}`, with `n` and `m` 255 or less | The same quantifier |
| A lazy quantifier, for example `*?` | The greedy quantifier. Both match the same whole values |
| `(…)` and `(?:…)` | `(?:…)` |
| `\|`, `^`, `$` | The same |
| The `i` flag of a format pattern | The operator `~*` in place of `~` |

A `regex` constraint gets the same anchors as in the Valibot schema: `^(?:<pattern>)$`. Examples from the `postgres` test fixture:

| `regex` | Condition |
| --- | --- |
| `[A-Z]{3}-[0-9]{4}` | `VALUE ~ '^(?:[A-Z]{3}-[0-9]{4})$'` |
| `\w+\.\d+` | `VALUE ~ '^(?:[A-Za-z0-9_]+\.[0-9]+)$'` |
| `(?:0x)?[\da-fA-F]{2,4}` | `VALUE ~ '^(?:(?:0x)?[0-9a-fA-F]{2,4})$'` |

### Parts outside the subset

| Part | Reason in the message |
| --- | --- |
| Lookahead, lookbehind and named groups: `(?=`, `(?!`, `(?<` | `lookaround and named groups have no translation` |
| A back reference: `\1` to `\9`, `\k` | `"\1" has no translation` |
| A word boundary: `\b`, `\B` | `"\b" has no translation` |
| A property escape such as `\p{L}`, and each other escape of a letter | `"\p" has no translation` |
| `\D`, `\W` or `\S` in a bracket | `"\D" inside a bracket has no translation` |
| A count above 255, for example `a{1,300}` | `a count above 255 has no translation` |
| `[^]`, `[]`, a `[` in a bracket, `\0` | A reason that names the part |

## Tables

### Root tables

Each entity in `tables` is a root table. Its columns come in the sequence of its `fields` list:

| Field reference | In the root table |
| --- | --- |
| `ref: <field>`, with no `many` | A column with the domain of the field |
| `link: <entity>`, with no `many` | A column with the domain of the key field of the linked entity, and a foreign key to its root table |
| `ref: <entity>`, or any reference with `many` | No column. A child table |

A column is `NOT NULL` if its field reference has `required: true`. After the columns comes `CONSTRAINT "<table>_pkey" PRIMARY KEY ("<key column>")`. The key column is the property of the `key` of the entity. Then come the checks of the invariants.

### Child tables

A property with `many`, or with an embedded entity, is a child table. A row of the child table holds one item of the list, or the embedded object.

| Part | Content |
| --- | --- |
| Key columns | The key columns of the parent table, with their domains. Then `"position" INTEGER NOT NULL CHECK ("position" >= 0)` for a list. A `position` of the parent becomes `"<property of the parent>_position"` |
| Other columns | For an embedded entity: the columns of the entity, as in a root table. For a list of values or links: one column with the property name, `NOT NULL`, with the domain of the field or of the key field |
| Primary key | The key columns. Thus an embedded entity with no `many` has one row at most for each parent |
| Foreign key to the parent | The parent key columns reference the parent table, `ON DELETE CASCADE`. When the shell deletes a parent row, Postgres deletes its child rows |
| Unique constraint | If the list has `unique: true`. For a list of an embedded entity: `UNIQUE (<parent key columns>, <key column of the entity>)`. For a list of values or links: `UNIQUE (<parent key columns>, <value column>)` |
| Checks | The checks of the invariants of the embedded entity |

The `position` holds the sequence of the list, from `0`. The shell writes it, and reads the items `ORDER BY "position"`.

The child table of the coverages of a policy:

```sql
CREATE TABLE "policy"."policy__coverages" (
  "policy_id" "policy"."policy_id_value" NOT NULL,
  "position" INTEGER NOT NULL CHECK ("position" >= 0),
  "peril" "policy"."peril_value" NOT NULL,
  "limit" "policy"."limit_value" NOT NULL,
  "note" "policy"."note_value",
  CONSTRAINT "policy__coverages_pkey" PRIMARY KEY ("policy_id", "position"),
  CONSTRAINT "policy__coverages_parent_fkey" FOREIGN KEY ("policy_id") REFERENCES "policy"."policy" ("policy_id") ON DELETE CASCADE,
  CONSTRAINT "policy__coverages_peril_key" UNIQUE ("policy_id", "peril"),
  CONSTRAINT "limit_is_positive" CHECK ("limit" > 0)
);
```

### Links

A link column holds the value of the key of the linked entity. If the linked entity is in `tables`, the file adds a foreign key after all the tables:

```sql
ALTER TABLE "policy"."policy" ADD CONSTRAINT "policy_holder_fkey" FOREIGN KEY ("holder") REFERENCES "customer"."customer" ("customer_id");
```

The foreign keys come last, so links can make a cycle. A list of links has a foreign key on each row of its child table. If the linked entity is not in `tables`, the column has no foreign key, and the plugin reports `unenforced-in-sql`.

### Counts

A `CHECK` sees one row, so it cannot count rows. A count is thus a constraint trigger:

| Field reference | Count |
| --- | --- |
| `many` with `minItems` or `maxItems` | Between `minItems` and `maxItems` rows |
| `many` with neither | No count |
| `ref: <entity>` with no `many`, `required: true` | Exactly 1 row |
| `ref: <entity>` with no `many`, `required: false` | No count. The primary key allows 1 row at most |

For each count, the file has three functions in the schema of the child table, and two constraint triggers:

| Statement | Job |
| --- | --- |
| `"<child table>_count"(<parent key>)` | If the parent row exists, it counts the child rows of the parent. If the count is outside the limits, it raises an error |
| `"<child table>_count_parent"()` | The trigger function on the parent table. It calls the count for the new row |
| `"<child table>_count_item"()` | The trigger function on the child table. It calls the count for the parent of the new row and of the old row |
| `CREATE CONSTRAINT TRIGGER "<property>_count" AFTER INSERT OR UPDATE ON <parent table>` | Runs for each parent row that the transaction writes |
| `CREATE CONSTRAINT TRIGGER "<property>_count" AFTER INSERT OR UPDATE OR DELETE ON <child table>` | Runs for each child row that the transaction writes or deletes |

The two triggers are `DEFERRABLE INITIALLY DEFERRED`. Postgres runs them when the transaction commits. Thus the shell can write the parent and its items in any sequence, in one transaction. A count that is not correct makes the `COMMIT` fail with this error:

| Part of the error | Value |
| --- | --- |
| SQLSTATE | `23514` (`check_violation`) |
| Constraint | `<property>_count`, for example `coverages_count` |
| Schema and table | The schema and the name of the parent table |
| Message | `<entity URN>: "<property>" has <n> item(s); it must have <limits>`. The limits are `between <min> and <max>`, `at least <min>`, `at most <max>` or `exactly <n>` |

Example: `urn:acme:insurance:policy:entity:policy: "coverages" has 0 item(s); it must have between 1 and 3`.

## Invariants

Each invariant becomes a named `CHECK` on each table that stores its entity: the root table, or each child table of the entity. The name is the identifier of the invariant. The checks come in URN sequence.

| Rule element | SQL |
| --- | --- |
| A field or a link | The column, in double quotes |
| A number | The number |
| A text literal of a `date` | `DATE '<day>'` |
| A text literal of a `timestamp` | `TIMESTAMPTZ '<t>'` |
| A text literal of a `decimal` | `'<n>'::NUMERIC` |
| A text literal of a different primitive | `'<text>'` |
| `true`, `false` | `TRUE`, `FALSE` |
| `a + b`, `a - b` | `(a + b)`. On `integer`, `(a::BIGINT + b)`, so that the sum cannot overflow |
| `=`, `!=`, `<`, `<=`, `>`, `>=` | `=`, `<>`, `<`, `<=`, `>`, `>=` |
| `a and b`, `a or b` | `(a AND b)`, `(a OR b)` |
| `not a` | `NOT (a)` |
| `x is present`, `x is absent` | `"x" IS NOT NULL`, `"x" IS NULL` |

Each comparison follows the primitive, as in the Valibot schema: a `decimal` compares exactly, a `date` as a day and a `timestamp` as an instant.

A `CHECK` fails only if its condition is false. A condition with `NULL` is not true or false. A guard such as `deductible is absent or …` makes the condition true when the value is absent. Thus the check gives the same result as the rule. Refer to [The rule language](./rule-language).

```sql
  CONSTRAINT "deductible_below_premium" CHECK (("deductible" IS NULL OR "deductible" < "premium")),
  CONSTRAINT "term_is_positive" CHECK ("expiry_date" > "effective_date")
```

A rule that names a list or an embedded entity, for example `tags is present`, has no check. The rows of a child table are not in the row that a `CHECK` sees. The plugin reports `unenforced-in-sql` and writes a comment after the comments of the table:

```sql
-- Not enforced here: urn:demo:store:shop:invariant:tagged (tags is present).
```

## Comments

The file writes the URNs into the database with `COMMENT ON`. The shell can read them from the system catalogs, and map a Postgres error back to the manifest.

| Statement | Text |
| --- | --- |
| `COMMENT ON DOMAIN` | `<field URN> — <description>`, or the URN only if the field has no `description`. For a deprecated field, ` (deprecated: superseded by <URN>; sunset on <date>)` follows |
| `COMMENT ON TABLE`, root table | `<entity URN> — <description>`. For a deprecated entity, the same mark as a domain follows |
| `COMMENT ON TABLE`, child table of an embedded entity | `<entity URN> (embedded in <parent entity URN> as <property>)` |
| `COMMENT ON TABLE`, child table of a list of values or links | `<field URN or linked entity URN> (a list in <parent entity URN> as <property>)` |
| `COMMENT ON COLUMN`, field | `<field URN>` |
| `COMMENT ON COLUMN`, link | `<linked entity URN> (a link: the value of its key)` |
| `COMMENT ON CONSTRAINT`, invariant | `<invariant URN> — <message>` |

The key columns and the `position` of a child table have no comment. A schema has no comment.

The mark of a deprecated field or entity has `superseded by <URN>` and `sunset on <date>` only if the field has them, separated by `; `. With neither, the mark is ` (deprecated)`. From the insurance domain:

```sql
COMMENT ON DOMAIN "policy"."note_value" IS 'urn:acme:insurance:policy:field:note — Free text about a coverage (deprecated: superseded by urn:acme:insurance:policy:field:remark; sunset on 2027-06-30)';
```

The comments of child tables, columns and constraints have no mark.

## Errors from Postgres

Each rule has a known SQLSTATE and constraint name. The insurance tests make sure of the codes in the last column:

| Rule | SQLSTATE | Constraint | Insurance example |
| --- | --- | --- | --- |
| A field constraint | `23514` | The identifier of the field | `premium`, for a premium of `1.005` |
| `required: true` | `23502` | None | |
| The key | `23505` | `<table>_pkey` | |
| `unique` | `23505` | `<child table>_<column>_key` | `policy__coverages_peril_key`, for two coverages with the peril `fire` |
| A link | `23503` | `<table>_<column>_fkey` | `policy_holder_fkey`, for a holder that is not a customer |
| An invariant | `23514` | The identifier of the invariant | `limit_is_positive`, for a limit of `0` |
| A count | `23514`, at `COMMIT` | `<property>_count` | `coverages_count`, for a policy with no coverages |
| A `position` below 0 | `23514` | `<child table>_position_check`. Postgres makes this name | |

## Rules that the SQL does not enforce

If a rule has no exact SQL form, the plugin does not write an approximate one. It reports `unenforced-in-sql`. The Valibot schema at the boundary still enforces the rule.

| Case | Comment in the SQL | Example message |
| --- | --- | --- |
| `format: uri`. Valibot uses the URL parser, which has no SQL form | Yes, before the domain | `urn:demo:store:shop:field:site: format uri: Valibot checks it with the URL parser, which has no SQL form; the SQL does not enforce it, and the Valibot schema at the boundary still does` |
| A `regex` outside the subset | Yes, before the domain | `urn:demo:store:shop:field:tag: regex (?!x)[a-z]+: lookaround and named groups have no translation; …` |
| A link to an entity that is not in `tables` | No | `urn:demo:store:shop:entity:item: the link "product" to urn:demo:store:shop:entity:product: that entity is not a table in the postgres config, so no foreign key can name it; …` |
| A rule that names a list or an embedded entity | Yes, after the comments of the table | `urn:demo:store:shop:invariant:tagged: the rule tags is present: "tags" is a list, which is rows of a child table, and a CHECK sees one row; …` |
| A list with `required: false` | No | `urn:demo:store:shop:entity:item: the optional list "tags": no rows can mean absent or empty, so the SQL keeps them apart only as no rows; …` |

The comment before a domain has this form:

```sql
-- Not enforced here: format uri: Valibot checks it with the URL parser, which has no SQL form.
CREATE DOMAIN "shop"."site_value" AS TEXT;
```

The position of the diagnostic is the entry of the field, the entity or the invariant in the manifest. With `unenforced: 'error'`, each case is an error, and `compile` writes no files.

An absent optional list and an empty list are both no rows. If an optional list has `minItems`, the count trigger accepts a parent with no rows, because the list can be absent. A parent with one or more rows must have the count.

## Limits

The SQL is a second check after the Valibot schema. Some values pass one check and not the other. The tests of the plugin found these differences with PGlite, which is Postgres 18.7:

| Value | Valibot | Postgres |
| --- | --- | --- |
| A `date` in the year 0000, for example `0000-01-01` | Accepts it | Refuses it: `date/time field value out of range` |
| A `string` with the character U+0000 | Accepts it | Refuses it. `TEXT` cannot hold U+0000 |
| A text form that the primitive does not use, for example `1e3` or `1.` for a `decimal`, or `2026-1-1` for a `date` | Refuses it | Accepts it. A domain sees the value, not the text that the shell sent |

A driver gives some values in a different form from the core. node-postgres gives `DATE` and `TIMESTAMPTZ` as JavaScript `Date` objects, and `NUMERIC` and `BIGINT` as strings. Postgres writes a timestamp as `2026-01-31 09:30:00+00`. The shell must change these values to the form of the primitive before it calls `executeOperation`.

urn-forge does not have these parts at this time. Refer to [Scope](./scope):

- Migrations, and a comparison of two schemas.
- Code that reads and writes rows.
- Indexes other than the primary keys and the unique constraints.
- Databases other than Postgres.
- A gate of `verify` that applies the SQL to a database. Gate 4 compares only the text of the file.

## Postgres version

The file is for Postgres 14 or later. `scale()` needs Postgres 13 or later, and the Postgres project no longer supports version 13. The tests apply the SQL with PGlite 0.5.17, which is Postgres 18.7.
