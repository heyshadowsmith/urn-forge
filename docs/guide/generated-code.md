# Generated code

The `urn-forge compile` command writes two TypeScript files in the `--out` directory. Commit these files to the repository. Gate 4 makes sure that they are the same as a new compile, and your core imports from them.

| File | Plugin | Contents |
| --- | --- | --- |
| `domain.schemas.generated.ts` | Valibot plugin | One branded schema for each field, one object schema for each entity, and their input and output types |
| `domain.runtime.generated.ts` | FCIS plugin | Handler types, `DomainCoreImplementation`, `DispatchMap` and `executeOperation` |

## The header and the fingerprint

Each generated file starts with these two lines:

```ts
// @generated by urn-forge 0.1.0 — do not edit
// fingerprint: sha256:<64 hex digits>
```

The fingerprint is a SHA-256 hash of five inputs:

- The canonical IR.
- The plugin configurations.
- The urn-forge version.
- The name and version of each plugin.
- The primitives and their constraints, and the kinds, that urn-forge knows. The generated code lists the primitives. Thus a new primitive changes the generated code, and the fingerprint must change too.

As a result, a change to the manifest, to the generator or to a plugin changes the header of each file. This occurs also if the other lines of the file do not change.

The output is deterministic. The compiler does not read the clock, the environment or random values. It sorts all items by URN in the sequence of the characters, not in the sequence of a locale. It writes UTF-8 text with `\n` line endings and one newline at the end.

## Schemas

Each field becomes a `v.pipe`. The pipe validates the primitive and applies the constraints in a fixed sequence. Then it ends with `v.brand('<field URN>')`. Each entity becomes a `v.object` of its field schemas. The plugin puts each field with `required: false` in `v.optional`.

Each field and each entity has three exports. The name of each export comes from the brand identifier:

| Export | Example | Description |
| --- | --- | --- |
| `<Brand>Schema` | `ArithmeticDivisorSchema` | The Valibot schema |
| `<Brand>` | `ArithmeticDivisor` | The parsed, branded type (`v.InferOutput`) |
| `<Brand>Input` | `ArithmeticDivisorInput` | The input type, without the brand (`v.InferInput`) |

## Runtime

### Handler contracts

Each operation has a handler type. **The input has a brand. The output does not have a brand.**

```ts
export type ArithmeticSafeDivideHandler = (
  input: s.ArithmeticDivision,
) => s.ArithmeticDivisionResultInput;
```

A handler returns the output shape without the brand, because the core must not make brands. The shell parses the output, and this parse adds the brand. Handlers are synchronous. The MVP has no declared errors. As a result, a handler returns the output directly, without a `Result` wrapper.

### The registry

`DomainCoreImplementation` gives the handler type for each operation URN. Declare your core with `satisfies`:

```ts
export const core = { … } satisfies DomainCoreImplementation;
```

Then `tsc` refuses a handler that is not there, a handler that is not in the contract, and an output of the wrong type. `tsc` also finds the parameter types of each handler from the clause. Gate 1 makes sure that the `satisfies` clause is in the file.

### `executeOperation`

```ts
executeOperation(urn, rawPayload, core): ExecuteResult
```

1. **It finds the operation.** If the URN is unknown, it returns `{ ok: false, kind: 'UnknownOperation' }`.
2. **It parses the input** with the input schema of the operation. If the parse fails, it returns `{ ok: false, kind: 'InputRejected', issues }`. It does not call the handler.
3. **It calls the handler** with the branded input.
4. **It parses the output** with the output schema, which adds the brand. If the parse fails, it returns `{ ok: false, kind: 'ContractViolation', issues }`. This result shows a bug in the core, not an error of the user.
5. **If all steps are correct,** it returns `{ ok: true, urn, output }`. The type of `output` is specific to the operation.

Each issue has three properties: the payload `path` (for example `divisor`), the `fieldUrn` of the field, and a message:

```ts
executeOperation('urn:demo:math:arithmetic:operation:safe_divide', { dividend: 1, divisor: 0 }, core);
// {
//   ok: false,
//   kind: 'InputRejected',
//   urn: 'urn:demo:math:arithmetic:operation:safe_divide',
//   issues: [{ path: 'divisor', fieldUrn: 'urn:demo:math:arithmetic:field:divisor', message: 'Invalid value: Expected !0 but received 0' }],
// }
```

### `DispatchMap`

`DispatchMap` contains the input schema and the output schema of each operation. It also contains data for each property: the field URN, the primitive, and if the property is mandatory.

- `executeOperation` uses this data to put the field URN on each issue.
- The [Gherkin steps](./gherkin-steps) use this data to convert table cells.
